# 肉品加工：升級與驗證

## 功能

正式生產新增 `meat_processing`。使用既有產品、批次、角色、庫存與簽名元件，新增逐版本保存的肉品加工明細。

1. 在產品管理建立「肉品加工」產品，例如豬肉分切。
2. 為各產出建立以 `kg`／`公斤` 管理的半成品或成品，設定允許庫位。現有以包數管理的品項不會自動轉換單位。
3. 如有需要，建立明確適用「肉品加工」的包裝類型；`both` 仍只適用成型與熱加工。
4. 在肉品加工入口建立批次、填寫原料與工序、記錄各項產出及損耗。投入包含醃料及水；溫度欄位只保存實測值。
5. 儲存明細版本，完成簽名送審；QA 簽名後鎖定，再辦理入庫。已覆核資料更正須作廢重建。

原料用量用於追溯，原料出庫仍由既有庫存操作處理。庫存仍按品項與庫位管理，不提供批號庫存餘額、成本核算或自動排程轉單。

## 升級步驟

部署時應使用既有正式環境流程；本次實作驗證未修改正式環境。

1. 暫停生產與庫存寫入，備份 PostgreSQL、Production Helper JSON volume、環境設定及目前 Git 版本。檢查備份可讀後才升級。
2. 先在資料庫副本套用 `database/migrations/20260915_meat_processing.sql`，確認既有批次數量與入庫餘額一致。升級腳本可重複執行，不刪除舊資料。
3. 查詢 `SELECT * FROM prod_batch_type_migration_review;`，記錄無對應產品的歷史批次。這些批次保留 NULL 類型與原本的產品查詢行為，不自動猜測分類。
4. 建置並更新後端與前端。後端啟動會先執行原有 migrations，再執行相同的肉品升級 SQL；新 enum 值會先單獨提交。
5. 核對三個產品類型及 `open / packed / closed` 批次 enum；肉品四個操作狀態保存在肉品主記錄，不另擴充批次狀態。
6. 檢查健康端點、肉品入口、既有成型／熱加工頁面，以及各角色權限，再恢復寫入。

不使用 `docker compose down -v`。升級為增量新增結構；需要回退應停寫並依備份恢復相容的程式及資料庫，不移除已產生的肉品記錄或 enum 值。

## 測試

後端使用 `backend/requirements.txt` 的版本。提供隔離 PostgreSQL 管理連線，測試會建立隨機名稱的資料庫副本，並在結束時只刪除自身建立的資料庫。

```powershell
$env:PYTHONPATH = 'backend'
$env:TEST_MEAT_ADMIN_URL = 'postgresql://postgres@127.0.0.1:55439/postgres'
python -m pytest backend/tests/test_meat_processing.py -q
npm run build --prefix frontend
```

測試連線須指向測試 cluster，使用可建立資料庫的帳號。未設定 `TEST_MEAT_ADMIN_URL` 時只執行純 schema／SQL 同步檢查，整合測試會明確標示 skipped。

涵蓋：

- 舊 schema 含成型、熱加工與無法對應產品的批次，啟動升級兩次後再複製為每項測試的獨立資料庫。
- 多原料、醃料增重、多產出、多庫位、差額說明、來源關聯、公斤單位及時間驗證。
- 明細歷史、過期版本、缺少簽名、角色限制、覆核鎖定與舊 API 繞過防護。
- 重複入庫、兩個批次同時入庫、實際過帳後發生錯誤的完整交易回滾，以及作廢沖回。
- 產品匯入與原有成型／熱加工包數入庫回歸。

本機另以 PostgreSQL 16.13 驗證完整 `database/init.sql` 與後端啟動。瀏覽器驗證涵蓋 390px 手機與桌面寬度、儲存新版本、實際繪製簽名、QA 鎖定、入庫，以及舊批次 URL 導向肉品頁面。

庫存寫入使用資料表交易鎖序列化過帳、作廢及盤點確認；在大量並行庫存寫入環境部署前，應依實際負載觀察等待時間。讀取庫存餘額不會被此鎖阻擋。
